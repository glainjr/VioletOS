# Open Runtime

The phone's apps are open apps, written in Rust: **Home**, **Settings**, **Ladybird Browser**, **Bitchat**, **Violet Agent** and **Locomo Music** ([apps/open](../../apps/open), sharing the [violet](../../apps/lib/violet) crate for the devices, drawing, text and HTTPS with rustls). Music streams the *Glass Orchard* album from the Rose Music library over HTTPS, decodes its MP3s itself (symphonia) and plays 48 kHz PCM through `/dev/violet/audio`, with a full-resolution player drawn into `/dev/violet/screen`. Home fetches the time from wttr.in itself; no URL, decoder or playback state lives in an OS service. Home is the main screen on both targets; the phone's settings are in the Settings app.

The Open Runtime runs ordinary Linux ARM programs on VioletOS, with no Linux kernel anywhere. A static binary built for `armv7-unknown-linux-musleabihf`, a Go program built with `GOOS=linux GOARCH=arm GOARM=7`, or a Python script with a `#!/bin/python3` line goes into `/apps` and runs as it is. It implements the [open app model RFC](../../docs/open-app-model-rfc.md).

## Try it

Run `make emulator`: it boots to Home, which shows an icon for each titled app (one with an `app.txt`, or one the agent installed); tapping one runs it. `apps` in `/dev/violet/sys` shows a plain list of every program in `/apps`. Programs that print go to the Open Runtime's log. In QEMU the log is a page of guest memory at `0x49220000`; on the handset, `build/moto-package open-log` prints it, and `build/moto-package open-run=/apps/NAME` starts a program over USB.

On the handset, `build/moto-package open-push=NAME < FILE` installs a program into `/apps` over USB without a reboot (about 400 KB/s; it lasts until the next restart), so the phone keeps its Wi-Fi connection while you iterate. `open-run` of a program that is already running replaces it.

`make test-open-apps` drives the built-in apps: Stopwatch keeps its time in `/data` across a restart, Sounds plays the chime, and Weather fetches live conditions (skipped offline).

`make test-open` starts each test program and checks its output, the frames drawn through `/dev/violet/screen`, taps, the PCM it plays and the trip to Home and back.

## Building programs for /apps

[tools/build_initfs.py](../../tools/build_initfs.py) builds the image from `apps/open`. Each folder becomes `/apps/NAME`:

- `Cargo.toml`: a member of the Cargo workspace in [apps/Cargo.toml](../../apps/Cargo.toml), built with crates for `armv7-unknown-linux-musleabihf` (ring, under rustls, compiles a little C with the NDK's clang).
- `main.rs`: built as a static Rust `std` program with `rustc` alone. Needs `rustup target add armv7-unknown-linux-musleabihf`.
- `main.go`: built with Go for `linux/arm`, `GOARM=7`, `CGO_ENABLED=0`.
- `main.c`: built against musl with the NDK's clang. Build the musl sysroot once with `python3 tools/build_python.py musl`.
- An `app.txt` names the app; titled apps come first in the list. The handset image leaves out Python and the network test programs (`HANDSET_SKIP`) to fit its boot partition.
- Anything else is copied as it is. A file starting with `#!` runs under the named interpreter; a `.py` file without one runs under `/bin/python3`; a folder runs its `main` or `main.py`.

`python3 tools/build_python.py python` cross-builds CPython 3.12 statically against musl (with zlib) and the image picks it up as `/bin/python3` and `/lib/python3.12`. It needs Homebrew's `python@3.12` on the Mac. Downloads are pinned by SHA-256.

QEMU loads the image uncompressed at `0x4a000000`. The handset carries it gzip-compressed as its boot image's ramdisk, where the stock Android ramdisk used to be; the loader copies it to `0xc0000000` and the Open Runtime unpacks it at start (about 3 seconds for 20 MB on the phone).

## How it works

```
 app thread ── svc #0 (Linux syscall in r7) ──► seL4: unknown syscall ──► fault endpoint
                                                                             │
 Open Runtime (component 24) ◄──────────────────────────────────────────────┘
   syscall.rs: Linux ARM EABI calls       device.rs: /dev/violet/{screen,events,sys,audio,camera}, hci.rs: /dev/violet/hci
   procmgr.rs: address spaces, ELF        fs.rs: /apps image + writable in-memory layer
   pool.rs: physical pages for apps       Runtime client 9: focus, touch, Home
```

- **Processes.** The supervisor gives the Open Runtime its own CSpace (16K slots), page directory, the ASID pool, 4 MiB of kernel memory and a pool of physical memory (384 MiB in QEMU, 256 MiB on the handset). The Open Runtime makes each app's page directory, CNode and threads itself and is their fault handler, so an app's crash ends that app and nothing else.
- **System calls.** seL4's system calls use negative numbers in `r7`; Linux's are positive, so a Linux `svc #0` reaches the Open Runtime as an unknown-syscall fault carrying `r0`–`r7`. The reply sets `r0` and moves the restart address past the `svc`. Calls that must wait (futexes, `read` of events, `poll`, `epoll_wait`, `nanosleep`, a full audio ring) keep the thread's reply capability and answer later. About 150 calls are handled; [syscall.rs](syscall.rs) lists them.
- **Memory.** Pages are 64 KiB, mapped on first touch. Regions still start on any 4 KiB boundary, as Linux allows. `mmap`, `munmap`, `mprotect` and `brk` maintain the regions; every pool page stays mapped in the Open Runtime as well, so reading app memory is a plain load.
- **Threads.** `clone` makes an seL4 thread in the same address space. The thread pointer is `TPIDRURO`, as on Linux; the kernel is built with `KernelArmTLSReg=tpidruro` and the Open Runtime sets it with `seL4_TCB_SetTLSBase`. seL4 clears the Thumb bit whenever registers are written, so new threads start at a one-instruction ARM trampoline (`ldr pc, [pc, #-4]`) that jumps to the Thumb or ARM target.
- **Screen and touch.** The Open Runtime is Runtime's client 9. The boot launcher hands it focus as soon as Runtime answers; it then draws the app in front (Home, unless another app is open) directly to the framebuffer. It samples touch every 4 ms and passes each change (down, a finger that moved, up) to the app in front. An app's surface is two 720 × 1600 BGRA8888 buffers that the app maps with `mmap`; `write` of a `PresentRect` copies that rectangle to the screen. Holding the top edge for a second, or writing `home` to `/dev/violet/sys`, leaves the app running in the background.
- **Frames** ([docs/8ms-frame-pipeline-rfc.md](../../docs/8ms-frame-pipeline-rfc.md)). Rust apps draw straight into the mapped surface (`Screen::canvas` in the violet crate), redraw only what changed and present just that rectangle. On the handset a present never tears: [scanout.rs](scanout.rs) reads the panel's scan line from the display engine and copies only while the panel is not reading those rows; otherwise the presenting thread waits (a full frame waits for the panel to near its last line, at most one frame). `ioctl(SCREEN_IOC_WAIT_VSYNC)` blocks until the next frame starts. In QEMU, presents tell the Mac viewer which rows changed, and it redraws at the Mac's refresh rate.
- **Touch interrupts and cores.** On the handset Touch reads each report on the controller's interrupt and passes it through a shared ring, signalling this process, so a touch reaches the app in front without a poll ([touch.rs](touch.rs)). With seL4 MCS the app in front runs on core 1 at priority 120 with 6 ms of every 8; the others run round robin at 100 on cores 2 and 3; this process and the services stay on core 0. Rust apps can scroll through `violet::Compositor`, which keeps drawing at the panel's rate while the app's main thread is busy.
- **Waiting for events.** The supervisor wires the ARM physical timer to a notification bound to the Open Runtime's thread. Between events it sleeps in one blocking receive, woken by an app's system call or by its own timer (the next touch poll, a thread's deadline, the scan line reaching a waiting present), at priority 150, above the services that poll at 100; long work (starting an app, a USB install) drops back to 100. If the timer does not fire at start, it polls as before. Runtime reads Audio's state from a page Audio publishes, so a status request no longer waits for Audio's hardware loop.
- **Measuring.** `frames` in `/dev/violet/sys` reports what presents cost, how long they waited for the panel, the time from a touch (or from focus) to the app's next present, and the gaps between touch polls; `bench tap X Y N` sends N synthetic presses to the app in front (`bench press X Y N` lifts the finger, a real tap, and also works on the app list). On the handset, `build/moto-package "open-run=@sys bench tap 140 860 20"` and then `"open-run=@sys frames"` put them in the open log.
- **Camera.** `/dev/violet/camera` gives the app on screen the rear camera's raw frames: each `read` returns a 32-byte `CameraFrame` header and the newest frame, once per frame ([abi.rs](abi.rs)). Opening it starts the [Camera service](../../services/camera/README.md); closing it, leaving the screen or the phone sleeping stops it. The frames are copied from a window Camera shares read-only, mapped cacheable: Camera invalidates each slot after the sensor's DMA writes it. The [Camera app](../../apps/open/camera/src/main.rs) develops them with `violet::camera`. The Open Runtime's package may be 0x60000 bytes (others 0x3e000), since its stack is not under its image.
- **Sound.** `/dev/violet/audio` takes 48 kHz s16 PCM (stereo, or mono with `AUDIO_IOC_CONFIG`). It fills a 64 KiB ring shared with the [Audio service](../../services/audio/README.md), which plays it at the shared volume through the speaker or headphones. Built-in sounds take precedence while they play.
- **Network.** TCP and UDP sockets use eight slots in pages shared with Radio, which runs them on its lwIP stack from its event loop ([sockets.c](../../targets/moto-g-pure/ip/sockets.c)): directly on a joined network, or, for TCP, through the phone's SOCKS5 relay in Phone Internet mode (UDP then fails with `ENETUNREACH`). A UDP socket takes a slot when it first sends to something other than the resolver, or asks for its address; its rings carry framed datagrams ([net.rs](net.rs)), a full ring drops one as a full interface queue would, `getsockname` gives the phone's real address and port on the network, and each new destination passes the Shield as a connect would. DNS queries (UDP to port 53) never leave the phone: the Open Runtime answers each name with an address in `198.18.0.0/15`, and a connect to one hands Radio the name, which it resolves (or the relay does). `/etc/resolv.conf`, `/etc/hosts` and the build machine's root certificates are in the image. In QEMU, [tools/net_relay.py](../../tools/net_relay.py) serves the same pages with the Mac's sockets; `VIOLET_NET_HOSTS` can point names elsewhere for tests, and `VIOLET_NET_UDP=0` refuses UDP like a network that blocks it.
- **Bluetooth.** `/dev/violet/hci` gives one open app at a time the Bluetooth controller's raw HCI ([hci.rs](hci.rs)): each `write` is one H4 command or ACL packet, each `read` one event or ACL packet, `poll` works, and both give `ENETDOWN` while the controller is off. On the handset Radio carries it over the connectivity chip's STP link ([bt.rs](../../targets/moto-g-pure/bt.rs)), so it runs while Wi-Fi is joined; in QEMU no controller is attached yet. [bitchat](../../apps/open/bitchat/README.md) is its first user.
- **Microphone.** `/dev/violet/mic` streams 16 kHz s16le mono samples to any reader: while one is open, Audio copies every sample into an 8-page ring after the PCM ring and the Open Runtime returns what arrived since the last read (blocking, `poll` works). The microphone stops when its app leaves the front and starts again when it comes back, except for the voice agent (`/apps/agent`): while it holds the microphone it keeps listening behind other apps, `status` says `listening=1` and Home shows a green microphone. A paired agent (`peer` in `/data/agent`) starts behind Home when Home starts.
- **Installed apps** ([appstore.rs](appstore.rs)). `install NAME TITLE` in `/dev/violet/sys` commits the agent’s staged program as `/apps/NAME` and gives it a Home icon under TITLE. After a successful replacement, the next launch starts the new version; `uninstall NAME` and `installed` complete it. Only `/apps/agent` may install; the agent and Settings (Agent Apps) may uninstall, which also ends a running copy. On the Moto, Storage keeps installed apps in the last 12 MiB of boot_b by default. The storage-preserving flash skips this range. If the owner has explicitly claimed Android userdata with `moto-flash --take-userdata`, Storage uses that partition and migrates the installed apps. QEMU uses sectors 4096 onward of its 16 MiB disk. Programs move through a 64 KiB window shared with Storage; a directory kept in two copies is rewritten only after the program is flushed, so a power cut leaves the old set or the new one. An install whose data starts with `VGZ1` (a gzip of a cpio archive) is a package: it is unpacked into `/bin` and `/lib` (nothing else) at every start, gets no Home icon, and Settings does not offer to delete it; Python reaches the handset this way.
- **Files.** `/apps`, `/bin` and `/lib` come from the image. Writes go to an in-memory layer over it. Files directly in `/data` (names of up to 16 letters, digits, `.`, `_` or `-`, up to 4 KiB) are kept across restarts by the Storage service ([data.rs](data.rs)): the Open Runtime loads them at start and writes one back after it changes. Storage keeps 32 such files for all open apps; everything else is lost at restart.
- **Home and /dev/violet/sys.** `/apps/home` starts the first time the open apps come to the front and stays running. `home` brings it back; `open PATH` brings an app to the front or starts it; `apps` shows the plain list of every program; `running` lists running programs; `status`, `audio`, `volume N|up|down`, `sound NAME`, `mic record|listen|off` and `log TEXT` cover the rest. An app leaving the front stops the microphone.
- **Wi-Fi.** `wifi scan`, `wifi list`, `wifi join ID [PMK]`, `wifi leave` and `wifi` (the state) in `/dev/violet/sys`, served by [wifi.rs](wifi.rs). Radio's requests run as Runtime tickets, so a join that takes seconds on the handset does not stop other apps. Any app can scan and read the state; only `/apps/settings` may join or leave. [Settings › Wi-Fi](../../apps/open/settings/src/wifi.rs) turns a typed password into the WPA2 key (PBKDF2-SHA1 with the SSID) and sends only the key. The auto-connector in wifi.rs rejoins the networks the app saved in `/data/networks`: 8 s after boot (a saved Phone Internet goes first), then with waits growing from 30 s to 10 minutes while none is in range, and every 30 s it checks a joined network is still joined. It tries each saved network in range, most recent first (a failed one waits for the next round, a refused key included: a lost handshake frame can look like a wrong key), and pauses after the app leaves a network.
- **Phone Internet and Bluetooth.** `relay` reports Phone Internet (`state=off|starting|waiting|joined|online|unavailable|busy`); `relay on CODE` and `relay off` start and stop it, from Settings only, which keeps its choice in `/data/relay`. Three seconds after boot the runtime turns a saved "on" back on. `bluetooth` answers whether the controller is up and whether an app has `/dev/violet/hci` open.
- **Radios.** `radios` reports `wifi=on|off bluetooth=on|off cellular=none gps=none`; `radios wifi on|off`, `radios bluetooth on|off` and `radios all off` change them, from Settings only ([radios.rs](radios.rs)). Wi-Fi off sends Radio a leave, which ends Phone Internet and powers the connectivity chip down, and refuses scans, joins and `relay on` (`error off`) and stops the auto-connector until it is on again. Bluetooth off resets the controller, refuses `/dev/violet/hci` (`EACCES`), and makes it read as off to an app already holding it. The choice is kept in `/data/radios`, which open apps can read but not write, rename or remove; the runtime applies it before the auto-connector or Phone Internet first look.
- **Policy.** Every `open` passes through [policy.rs](policy.rs); the default `OpenPolicy` allows everything.

## Not done yet

- Listening sockets and IPv6. TCP clients and UDP sockets work; `listen`/`accept` return `EOPNOTSUPP`.
- Larger persistent files. `/data` keeps 32 files of up to 4 KiB (installed programs have their own store).
- Signals are accepted but never delivered, so Go runs with `GODEBUG=asyncpreemptoff=1` and a fault ends the app.
- `fork` and `execve`. Programs can start threads but not other processes; `/dev/violet/sys` can `launch` another app.
- Dynamic linking. Programs must be static (static PIE works).
- Up to six apps at once, on four cores (the second cluster of the MT6765 is not used).
